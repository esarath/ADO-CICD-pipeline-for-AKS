4.1 Helm - the packaging layer

All strategies below are executed through the same Helm chart (helm/sample-app) via templates/deploy-helm-steps.yml. The chart carries: Deployment (probes, securityContext, resources), Service (slot-aware selector for blue-green), HPA, ServiceAccount (workload-identity ready), Ingress, NetworkPolicy.

helm upgrade --install sampleapp helm/sample-app \
  -n staging -f helm/sample-app/values-staging.yaml \
  --set image.repository=<acr>.azurecr.io/sampleapp \
  --set image.tag=1.4.0 --atomic --timeout 5m

--atomic auto-rolls-back on failure - the built-in safety net for every strategy below.

4.2 Rolling (default)

Mechanics: strategy=RollingUpdate, maxUnavailable=0, maxSurge=1 - new pods come up before old ones die; one extra pod of capacity needed.

ProsCons
Zero config, minimal extra capacity (+1 pod), gradual exposure, native rollback via helm rollback Both versions serve traffic mid-rollout - no instant revert; a bad pod mix can confuse stateful clients

Use when: stateless services, backward-compatible API/schema changes - the sensible default for this POC.

4.3 Blue-Green

Mechanics: deploy a full parallel release sampleapp-green into the same namespace, wait healthy, then patch the stable Service selector slot: blue → green. Instant cutover, instant rollback (patch back). Implemented in deploy-helm-steps.yml via strategy=bluegreen.

ProsCons
Atomic cutover & instant rollback, full pre-prod validation of the new stack, no mixed-version traffic 2× capacity during cutover (watch spot pool limits), DB schema must be compatible with both versions, in-flight requests on old pods dropped unless drained

Use when: releases that must cut over cleanly and revert instantly (e.g., payment flows, demos to stakeholders).

4.4 Canary

Mechanics: strategy=canary runs a small canary release alongside stable (e.g. 1 pod vs 2). Traffic splits roughly by replica ratio on ClusterIP; for precise 5/25/50% weighting use Flagger + Istio/NGINX (Day-2 add-on). Promote = scale canary up / make it stable; abort = delete canary.

ProsCons
Smallest blast radius, real-traffic validation, metrics-driven promotion Needs meaningful traffic + good metrics to be useful; without Flagger, weighting is coarse; session affinity complicates things

Use when: high-traffic user-facing services where regression cost is high. For a POC, demonstrate the coarse replica-ratio version.

4.6 GitOps alternative - ArgoCD

The YAML pipelines above use the push model (pipeline calls helm upgrade). ArgoCD flips it to pull: ArgoCD inside the cluster watches Git and converges the cluster to the declared state.

Push (pipelines + Helm)Pull (ArgoCD)
CredentialsPipeline needs cluster credentials (scoped by service connection)None stored outside the cluster - ArgoCD pulls Git
DriftNot detected out of the boxAuto-detected; selfHeal reverts manual edits
ApprovalAzure DevOps Environment approvalPR merge to release branch (or manual Sync)
AuditPipeline runsGit history = deploy history
FitSimpler, one pipeline does everythingBetter for many services/clusters; extra component to run

Install: gitops/argocd/install-argocd.ps1 then apply application-staging.yaml (auto-sync) and application-production.yaml (manual sync = approval).

4.7 Rollback cheat-sheet

# Helm history + rollback
helm history sampleapp -n production
helm rollback sampleapp <rev> -n production

# Blue-green: point stable service back
kubectl patch svc sampleapp -n production \
  -p '{"spec":{"selector":{"app.kubernetes.io/name":"sample-app","slot":"blue"}}}'

# ArgoCD: sync to previous commit, or selfHeal reverts manual drift automatically
